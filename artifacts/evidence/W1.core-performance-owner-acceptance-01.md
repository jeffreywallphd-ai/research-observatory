## Future refactoring candidate, not W1 work

Reassess Core cold-start loading and idle memory during a future mutable Wave's
planning. No new W1 correction task, product edit, repeated benchmark or expanded
profiling is authorized or needed by this record. Future implementation must be
selected and accounted for under that Wave's approved plan/refactoring budget.

Potential causes to investigate, not established explanations:

- Additional eagerly loaded application contracts, validators and service
  modules may add startup work and retained memory as capabilities accumulate.
  A nonqualifying import-only observation measured about 50 ms in the Core model
  module and about 546 ms cumulatively in the app module, including dependencies.
  These overlapping import timings are not additive and do not explain the
  packaged timing or memory regression by themselves.
- Eager validator/serializer construction is one possible optimization target.
  Deferred construction has not been implemented or shown to improve this build;
  it could instead shift cost to first use. Any future experiment must preserve
  cold/concurrent first-use validation, denial behavior and unchanged OpenAPI.
- The current package has more files than the baseline package (710 versus 661),
  but package growth alone does not establish a cause. Host/cache variation and
  other runtime effects were not isolated; do not attribute the result to them.

Stop this optimization investigation now. At future selection, profile before
changing code and measure both startup and first meaningful use; preserve the
current evidence and report tradeoffs rather than moving cost out of sight.
