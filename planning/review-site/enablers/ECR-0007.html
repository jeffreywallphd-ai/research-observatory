## 1. Decision requested

Approve one append-only W1 amendment owned by `CAP-01`, with one mixed
contribution and two ordered tasks:

1. `W1.A08.T01` consolidates the shared production styling foundation and
   brings every currently implemented W1 desktop surface into general visual
   and interaction alignment with Academic Minimal 1.5.
2. `W1.A08.T02` adds a deterministic live-product styling-conformance boundary
   so the actual React/Tauri frontend—not a copied reference fixture—is checked
   for reusable-style discipline, computed geometry, responsive behavior,
   themes, accessibility, and representative visual composition.

Conformance is deliberately not pixel-identical reproduction. Normative tokens,
semantic states, control geometry, spacing rhythm, content hierarchy,
responsive behavior, interaction states, and accessibility remain binding.
Illustrative copy, data, and exact page composition remain non-normative, and
small rendering differences that preserve those contracts are acceptable.

The currently implemented surfaces in scope are the application shell;
lock/recovery and service-boundary states; Projects; Project Home; Project
Settings; Application Settings / Security & sign-in; Research Intent; Audit &
Lineage including controlled recalculation; Task Center; Diagnostics; dialogs;
tables; forms; notices; and shared status/evidence panels. Later-Wave pages are
not pulled into W1.

## 2. Initiation assessment

### 2.1 Product and best-practice fit

The Vision and approved reference call for a quiet academic workbench with
consistent hierarchy, restrained density, predictable spacing, and reusable
semantic components. A small token-driven layout vocabulary is the sustainable
implementation fit: shared stack, cluster, grid, panel, form, notice, table,
dialog, and page-region rules should own common geometry, while page selectors
should express only genuine composition differences.

The selected direction keeps CSS close to the component boundary, uses logical
properties and semantic custom properties, favors low-specificity reusable
classes, and tests the built product at observable layout and interaction
boundaries. It does not introduce a CSS framework, CSS-in-JS runtime, or a
second token source.

### 2.2 Tested implementation baseline

The production frontend already imports the canonical reference token file
through `@research-observatory/ui-tokens` and has reusable typography, button,
field, table, dialog, notification, badge, boundary-state, and panel components.
Existing renderer tests cover substantial keyboard, focus, responsive,
reduced-motion, theme, workflow, and application-state behavior. These are
strong reusable boundaries.

The visible implementation nevertheless has a second page-specific styling
layer. `apps/desktop/src/app.css` and the component stylesheet contain roughly
three hundred selector blocks, including repeated control, card, table, notice,
and layout declarations. Several common containers rely on browser-default
child margins instead of an explicit content-flow contract. Production shell
geometry also diverges from the approved reference: for example, the sidebar
declares an 18 rem minimum around a 15 rem token, while the main region uses a
separate 80 rem width and lacks the reference page-content centering contract.
Those differences explain the inconsistent padding, margins, alignment, and
visual rhythm observed by the repository owner.

The current UI conformance profile validates the generated
`apps/desktop/dist` reference fixture. The real functional React product is
built separately in `apps/desktop/product-dist`; it is source-hash-bound and
covered by interaction tests, but it is not compared to the reference at the
same computed-geometry or representative screenshot boundary. A copied
reference page can therefore pass visual regression while the live product
drifts.

### 2.3 Refactor disposition

`W1.A08.T01` is bounded technical-debt refactoring plus defect correction. It
consolidates existing production styles and component composition without
changing accepted architecture or restructuring completed capability outcomes.
Its L estimate is 5 of the immutable 194-point approved-W1 baseline, or 2.6%,
within the standard 15% limit. `W1.A08.T02` is new verification/product-quality
work and is not counted as refactoring. No major refactor is authorized.

## 10. Alternatives

1. **Consolidate shared styles and add live-product conformance — selected.**
   This fixes the observed product quality and closes the verification gap that
   allowed drift.
2. **Patch spacing page by page.** Rejected because it would deepen duplicate
   styling and make later surfaces less consistent.
3. **Require exact pixel equality with reference mockups.** Rejected because
   mock content and composition are illustrative; exact equality would be
   brittle and would conflict with the requested general, not identical,
   alignment.
4. **Adopt a new styling framework.** Rejected as unnecessary foundational
   churn for a token and component system that already has sound boundaries.
5. **Defer to W6 or release qualification.** Available but not recommended;
   W1 would establish weak styling patterns and a misleading visual gate for
   every later desktop surface.
