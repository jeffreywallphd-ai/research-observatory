# Blind novice usability assessment — session 02

## Outcome

The native application became responsive and the still-blind agent attempted all
nine original tasks. It **could not create its own project or obtain a guided
next step**. Using the supplied sample as explicit assistance, it saved a draft
and verified that the text and revision survived closing/reopening. Theme,
keyboard navigation, policy information and support preview were usable.

The software is therefore usable for this limited assisted path, **not working
correctly end-to-end and not ready for W1 approval**. The earlier startup hang
remains unexplained; a successful retry and normal close are not a permanent fix.

Primary evidence: [actual-session transcript](W1.usability-blind-01.session-02.transcript.md),
sections 1–9. The [original nine tasks](W1.usability-blind-01.moderator.md),
[implemented action inventory](W1.usability-blind-01.report.md#actions-users-should-be-able-to-perform-now),
[exact build binding](W1.usability-blind-01.build.json), and
[earlier interrupted attempt](W1.usability-blind-01.transcript.md) remain available.

## Method and limits

One simulated novice agent, originally dispatched with `fork_turns=none`, received
only a test executable, synthetic data locations, ordinary UI-tool guidance and
neutral outcome tasks. It received no project source, prior findings, plans,
designs, diagnostics or hints about fixes. The same still-blind agent resumed
after the moderator verified responsive startup and basic interaction. It used
the native UI, not mocks, APIs, source inspection or developer tools. The
moderator issued no UI calls while the participant owned the window.

The transcript preserves spoken-style expectations, actions and observations,
not hidden reasoning. This is **not a representative human-participant study**:
do not infer population success rates, learning times or universal novice
preferences. Task durations were not measured. Occasional stale accessibility
snapshots/focus targeting are documented separately and are not UX findings.

No researcher data, sign-in, security/privacy changes, deletion, support export
or external send was used. The sample's draft revision 2 and the selected dark
theme remain. The agent closed the test window normally with Alt+F4. It did not
restart the entire application to verify that saved project state survives an
application restart; it verified project close/reopen in one application session.

The debug executable ran genuine Core from its repository fallback package.
Actual executable and all 710 package files match the frozen build inventory.
This is not standalone/release packaging qualification; see the separate
[startup/path diagnostic](W1.usability-blind-01.startup-diagnostic-02.md).

## Ranked findings and remedies

Priority describes this study's user impact, not a controlled task-review
disposition. Technical causes below are moderator analysis and were not supplied
to the participant. Recommendations are not implementation or new design approval.

### U01 — High: project creation has no usable completion or recovery path

Evidence: task 2. The project-action error appeared before a create submission.
The research-type selector stayed at `Loading governed use cases…`; Create was
disabled despite visible entered details. Participant: “I can’t choose a research
kind or confirm a save.”

This blocks the central new-user goal; it is not just a cosmetic affordance issue.
The error describes an unspecified project action and refers to `Core status`
without telling the user which read failed or providing an observed recovery
action. The source confirms the catalog read and create operation share generic
failure presentation, while a failed catalog leaves the selector's loading label.

Remedy: restore native catalog route parity; model service starting, catalog
loading, catalog failed and ready separately. Show a plain-language catalog
failure with an explicit read-only retry, preserve entered values, and explain
why Create is unavailable. Never automatically replay a project mutation or
supply an invented fallback catalog. This is principally existing A09.T02 scope.

Closure: actual native/Core cold-start and failed-catalog recovery; the participant
can choose research type, create once, see an explicit saved/open confirmation,
then close/reopen the new project without sample assistance. Denial and retry
tests must prove no unintended mutation.

### U02 — High: guided next-step failure leaves a saved project without direction

Evidence: task 4. The app reported that guided workflow could not load and previous
workflow context was cleared. Participant: “I can see tools to visit, but I can’t
tell which research step should come next.” Manual tool navigation and saved text
still worked; do not conflate this with lost project data.

Remedy: repair the real catalog/context loading path, retain authoritative
fail-closed behavior, and provide a specific retry/next safe action. Once loaded,
show the current step, why it matters, required decisions and a labeled next or
return action. Do not fabricate guidance from stale or mismatched authority.
Use existing approved guided-workflow contracts and A09.T02/T04 proof.

Closure: a new and reopened compatible project show the correct current step;
visiting a supporting tool and returning retains exact project/intent/step
authority. A failed reload explains recovery without implying that saved work
was erased.

### U03 — Medium: broad errors undermine trust in operations that actually work

Evidence: tasks 1, 3, 4 and 6. Ready labels coexist with workflow errors; the intent
page shows an intent-action failure, then a usable form, and errors return after
navigation/reopen. The participant nevertheless saves and recovers revision 2.
“The intent page first showed an error, then the form appeared.”

Moderator source inspection shows separate catalog and intent reads can affect
the same broad error area. A success in one dependency does not prove another
dependency recovered; simply hiding all errors would also be wrong.

Remedy: scope notices to the failed operation/dependency, separate service
availability from project-feature readiness, and keep save confirmation distinct
from an unavailable workflow catalog. Use bounded, actionable language such as
“Research types could not load” where that is the actual failure. Make status
changes available to assistive technology without stealing focus. This aligns
with [W3C status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

Closure: delayed and failed reads show the correct terminal state and recovery
action; successful draft saves state exactly what persisted; unrelated failures
remain truthful and do not masquerade as failed saves. Route/readiness correction
is already scoped; additional presentation changes require the governed reference
mapping, not an unreviewed copy rewrite.

### U04 — Medium: file-system terminology adds avoidable setup burden

Evidence: task 2 and sample assistance. The user-facing form requires an absolute
Parent directory, separate constrained Project directory name, and Project name;
opening requires a path to the folder containing `project.ro.json`. The agent
entered supplied exact paths. It did **not** fail because of an invalid path, so
that causal claim would be unsupported.

Remedy: implement the already-approved shared native folder chooser for create
and open; derive the safe child folder from the friendly project name, preview
the full destination, and preserve explicit selection/cancellation. Keep internal
manifest names and path syntax out of required novice input. Use concise labels,
help and format cues as supported by [W3C input guidance](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html).
This is A09.T03, not a second parallel folder implementation.

Closure: a participant with only a friendly project name and folder choice can
create/open; cancellation changes nothing; Unicode/spaces, reserved names,
collisions, inaccessible paths and keyboard focus meet the approved contract.

### U05 — Medium: Compare versions promises more than its result provides

Evidence: task 3. Clicking Compare versions produced revision number, use case,
unresolved count and hash summaries. Participant: “I don’t see a comparison of
the actual wording.” The source renders an ordered revision-summary list, not a
content diff. Preview revision effects was found but not activated; do not claim
that preview failed or does not exist.

Remedy: either accurately label this current view “Revision history,” or provide
a governed comparison showing the actual changed fields/wording, author rationale
and selected revisions. Keep hashes available in technical detail, not as the
primary explanation of what changed. Decide this through the applicable existing
intent acceptance contract/reference before implementation; it is not silently
added to A09's frozen catalog/folder scope.

Closure: a saved sentence change can be identified and distinguished from prior
wording before acceptance, or the limited history view is labeled honestly and
does not promise a diff. Do not auto-accept or weaken researcher review.

### U06 — Medium: technical language and unlabeled state dimensions cause uncertainty

Evidence: task 6. A closed project simultaneously displays `active` and `Closed`:
“It also still says ‘active,’ which is confusing.” The states can both be correct
(project lifecycle versus current open session), but their distinction is not
clear to this participant. Across the session it also identifies Core, governed,
durable work, egress, content hash and JSON as unfamiliar or uncertainty-inducing.

Remedy: lead with familiar task language, label lifecycle and session separately
when both are necessary, and retain precise technical identifiers in expandable
details/help. Examples for design consideration: “Background work” for the Task
Center concept, “Data leaving this computer” for egress, and “View technical
details” before JSON. These are proposals, not approved replacements for legal,
security or scholarly terminology. Preserve actual meaning and protection
disclosures. Natural navigation labels and grouping should follow the app's
experience contract and [Microsoft navigation guidance](https://learn.microsoft.com/en-us/windows/apps/design/basics/navigation-basics).

Closure: a novice can explain whether the project is currently open, whether it
is archived, whether a draft was saved, and what background work is listed,
without a glossary or interpreting a hash.

## Strengths to preserve

- `Saving locally…`, a specific revision number, and explicit “saved locally” /
  not-final feedback correctly separated durable drafts from acceptance.
- The sample draft survived project close/reopen. Acceptance stayed disabled for
  unresolved decisions; this study does not recommend relaxing that protection.
- Task Center's empty state was findable and explained what kinds of work belong
  there, although “durable” was unfamiliar.
- Dark theme, visible Shortcuts and Alt+H navigation worked in this session.
- “Offline · send nothing” and the plain included/excluded support lists were
  understandable. Keep these clear summaries; retain exact technical preview as
  secondary inspection, with no implied automatic transmission.

## Styling and reusable implementation

This study did not measure padding, margins, sidebar/footer geometry, contrast,
reflow or comprehensive keyboard accessibility. It supplies **no new independent
proof** that those earlier styling defects are fixed or unfixed. Retain the
existing A08 findings and their live geometry/conformance requirements.

Implement the resulting approved corrections through existing shared tokens and
components: one directory field, common labeled field/help/error composition,
shared loading/error/empty-state notices, reusable status badges, and the existing
page/stack/cluster/grid layout classes. Do not patch each page with duplicated
spacing rules or invent another token layer. Pair component tests with actual
native-path tests; renderer mocks alone did not expose this run's critical
catalog/navigation failures. Current approved-reference restoration and proposed
new wording/design changes must remain clearly distinguished.

## Technical blockers kept outside the UX transcript

1. **Unexplained startup hang:** user and Windows corroborated; recovered in a
   later attempt with no product-code fix. Repeat cold/restart qualification is
   required. The later normal close does not erase the failure.
2. **Packaged-resource path mismatch:** independently reproduced against compiled
   code. Safe equivalent Windows path representations are treated differently,
   causing debug fallback. Bounded A09.T02 correction and A09.T04 no-fallback
   packaged qualification were independently advised. Do not weaken path/file
   identity checks or claim executable-content authentication from this probe.

## Recommended continuation

Preserve this baseline and prioritize creation/catalog/next-step reliability,
then the approved shared folder UX and returned styling work. Record the narrow
resource-path correction in the relevant task-start acceptance map; do not edit
native product code under T01 or skip dependency order. Reference1.6 activation /
compatibility work remains T01; independent task/slice/Wave gates still apply.

Treat version-comparison semantics and broader terminology suggestions as
acceptance-bound follow-up findings requiring their applicable contract/reference
decision, not permission to expand the frozen amendment. No additional human
approval is requested by this assessment, and W1 passing is not yet approvable.

After the approved corrections, rerun the same nine neutral tasks against a new
hash-bound native build and fresh synthetic data. The current agent is blind to
implementation but now familiar with the UI: use a **fresh no-context agent** for
another first-use assessment, and optionally this agent for learned-use regression.
Then validate major conclusions with actual representative novice users; this
single agent simulation is diagnostic evidence, not a human usability benchmark.
