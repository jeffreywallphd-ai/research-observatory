## Owner direction, 2026-09-05

“Can you ensure that in dev and production that a default folder is pre-selected
for projects. I want to limit the user's need to think about folder structures.
Please add that to T03. Please continue working, following the workflow and

Interpretation: the new-project form should already have a usable, visible
default parent location, not merely offer a starting directory after the user
opens a picker. The ordinary path should require a friendly project name,
research details and explicit Create—not directory typing or a mandatory folder
choice. Keep Change folder available. Opening an existing project still requires
selection of the actual project; a parent container is not an openable project.

## Required acceptance coverage

- One native resolution policy supplies the same default in dev and production
  for the same Windows user. Do not derive it from checkout, working directory,
  executable location, debug flags, hard-coded usernames or an app-identifier
  variation used for the test harness.
- Show the chosen parent and generated complete destination before explicit
  Create. The existing shared DirectoryPickerField/Change folder interaction,
  slug stability, collision handling and read-only path preview remain.
- A valid current form selection is not replaced by late default resolution.
  Cancel preserves the prior selection and form; lock, close and stale/unmounted
  results retain the existing protected-generation behavior.
- Default discovery, form mount and folder selection must not create/open a
  project, silently grant access, migrate data or transmit anything. Any required
  directory provisioning must have an explicit authorized mutation boundary.
- Do not silently choose cloud-synced, redirected/network, protected or unusable
  storage merely because it appears as Documents. Retain local-first, current-user,
  path validation and no-overwrite guarantees. Do not claim that a local path can
  prove absence of every external backup/sync agent.
- Cover fresh user, existing default, missing/unavailable/denied location,
  Unicode/spaces, redirected/synced candidate, dev/release parity, cancellation,
  override persistence during the form, late responses and app lock/close. A
  native failure must provide safe recovery, never an editable-path workaround.
- Real Windows/native/Core creation must succeed from the default without
  requiring a folder dialog, then close/reopen the resulting synthetic project.

## Selected policy and independent preflight, 2026-09-05

Read-only source review by `t01_r02_independent_review` found the following
bounded policy compatible with the existing-parent contract. This is advisory

- Resolve Windows `FOLDERID_LocalAppData` and the existing `Research Observatory`
  product parent, identically in dev and production. This is the project parent,
  never its `security` or `security/profile-default` subtree. Normal Core actor
  initialization already uses this product parent; default discovery must not
  initialize a credential store or create a directory itself.
- A narrowly named read-only native resolver takes no caller-supplied path and
  returns an available validated location or a bounded failure. Bind it to the
  local main window and protected-action generation. Keep the purpose-specific
  folder picker request unchanged; discovery is not a fabricated user-selection
  event and grants no general filesystem operation.
- Validate existence, locality, canonical/reparse boundaries and existing Core

  recovery through Change folder; do not silently fall back to Documents,
  an account root, repository, temporary directory or the LocalAppData root.

  `main.py` can continue with no local actor after initialization failure. The
  resolver attests only to an existing validated location. Preserve ordinary
  Create authority checks; do not inspect secrets to infer stronger readiness.
- Preserve no-overwrite behavior, including a project named “Security” colliding
  with the existing sibling rather than entering, enumerating or replacing it.
  An unusual installation overlapping the candidate remains excluded.

Add explicit acceptance cases for no filesystem mutation before Create,
identical dev/production resolution, late resolution losing to a user choice,
lock/unmount races, missing/redirected/installation-excluded parents and the
security-name collision. Verify the normal fresh-user Core startup establishes
an eligible parent and actual default-based creation works. If that is not true,
do not conceal it with resolver-side provisioning: report the unmet case and
