## 2. Trigger evidence and exact failure

The approved W1.A03 recovery transition cannot be invoked after its required ordinary resume because it requires two different commits to be the same value:

1. `taskctl wave resume` starts from a clean commit and stores that pre-resume commit as `wave.campaign.base_sha`, then mutates `planning/backlog.yaml`.
2. The resume state must be committed before `taskctl recover`, because recovery requires a clean worktree.
3. `git_execution_identity` correctly requires `--base-sha` to equal the now-current committed `HEAD` for stale-writer protection.
4. `command_recover` also requires that same `--base-sha` to equal the earlier `wave.campaign.base_sha`.

Reproduction on the immutable stopped boundary:

| Boundary | Commit | Result |
|---|---|---|
| Resume input | `bf27fddd8e1732feadc698cd77f540ea9e1c7a0e` | Stored as the campaign base when W1 is resumed. |
| Committed resume state | `54d03055b1c6d9b702859d5fefbbac1e38de39df` | Required clean `HEAD` for the recovery compare-and-swap. |
| Recover using committed `HEAD` | `54d03055…` | Denied: exact T03 recovery base must match the resumed W1 boundary. |
| Recover using stored resume input | `bf27fddd…` | Denied: base SHA must equal current Git `HEAD`. |

The passing W1.A03 tests directly assigned both identities to one synthetic commit. The real-persistence fixture exercised atomic save and stale-writer denial but did not invoke the actual resume controller, commit its mutation, and then invoke recovery through the command boundary.

## 4. Selected design

### 4.1 W1.A04.B00 — durable resume-record bootstrap

The bootstrap adds the minimum generic controller and schema support needed to represent a committed resume boundary without an impossible self-reference.

Authorized implementation paths:

- `planning/backlog.schema.json`;
- `tools/taskctl.py`;
- `tests/foundation/test_taskctl_schema.py`; and
- `tests/foundation/test_taskctl_workflow.py`.

Required behavior:

1. A future `wave resume` appends a structured `resume_record` that binds the clean pre-resume Git commit, the prior PAUSED campaign boundary, branch, canonical worktree, profile, platform, actor, and timestamp.
2. The record is immutable once written for that resume attempt, is preserved through later task execution, and is validated against the live campaign projection.
3. The record does not claim to know the Git commit that will later contain itself. The clean current `HEAD` remains external execution identity and is checked at the command boundary.
4. Existing historical campaigns remain valid without invented records; a newly resumed revision-6 W1 campaign must contain the new record before exact recovery is legal.
5. Missing, malformed, rewritten, cross-Wave, wrong-branch/worktree/profile/platform, non-ancestral, duplicate, or stale resume records fail closed and do not mutate the backlog.
6. No task is recovered, claimed, reviewed, completed, or otherwise changed by B00.

B00 may not modify or invoke `command_recover`, alter T03, release the hold, resume W1, or change product/reference files. Its exact implementation and criterion evidence require independent control/security approval before W1.A04.T01 may be materialized.

### 4.2 W1.A04.T01 — committed-resume exact recovery repair

T01 applies the independently approved resume-record contract to the exact W1.A03 T03 recovery transition.

Required behavior:

1. Preserve every existing W1.A03 authority, historical T03 base/foundation/candidate/block/pause/reference/evidence binding, privacy/product recomputation, and BLOCKED-to-IN_PROGRESS limit.
2. Treat the resume record's pre-resume commit as immutable transition authority, not as the current compare-and-swap commit.
3. Treat the clean current full Git `HEAD` supplied through `git_execution_identity` as the sole stale-writer boundary for the recovery mutation.
4. Prove that current `HEAD` is the committed result of the exact recorded resume: strict ancestry, expected historical/current backlog projections, and an exact allowlisted state-view diff. No unrelated source, product, reference, evidence, policy, or controller byte may be hidden in the resume commit.
5. Revalidate the approved W1.A03 packet/task contract, adopted amendment checkpoint, released GRR-0001 hold, active resumed W1 lease, exact blocked T03 boundary, canonical recovery manifest, immutable Git objects, UI gate, and privacy/product checks immediately before one compare-and-swap save.
6. Add an isolated real-Git integration that invokes the actual resume controller, regenerates the required state views, commits that exact transition, invokes the actual recovery controller, and proves the sole lawful transition changes only T03 to `IN_PROGRESS` with the current committed `HEAD` as its new task base.
7. Add byte-stable denials for an uncommitted resume, extra commit, squashed or amended resume record, unrelated file in the resume commit, wrong predecessor/current head, wrong branch/worktree/profile/platform/actor, expired lease, altered hold/amendment/checkpoint/task/manifest, duplicate recovery, dirty tree, and competing writer.
8. Keep the live recovery command denied while W1.A04 is executing under the active hold. Actual T03 recovery occurs only after W1.A04 adoption, hold release, and an explicit ordinary W1 resume.

Authorized task paths are limited to the task controller/schema, their directly affected recovery/workflow/schema tests, the automation guidance needed to document the boundary, and generated planning/status views caused by governed transitions. No product, privacy, approved-reference, UI-evidence, capability-plan, slice-plan, acceptance, threshold, or release-gate byte may change.

## 7. Alternatives

1. **Append an immutable resume record and separate it from the current CAS head — recommended.** This represents both truths without self-reference and preserves stale-writer safety.
2. **Remove the campaign-base comparison.** Rejected because a merely clean current `HEAD` would not prove it contains the exact governed resume transition.
3. **Add a post-commit rebind command.** Rejected because rebinding would dirty the ledger again, recreate the same commit paradox, and add a second transition with no product value.
4. **Treat the resume input as the current head.** Rejected because it disables the existing clean-current-HEAD stale-writer guard and cannot survive the required resume commit.
5. **Replay T03 from a new product candidate.** Rejected as destructive churn that obscures the already reviewed implementation lineage.
6. **Defer W1 or bypass the ledger.** Deferral leaves W1 blocked; bypass would defeat the exact controls restored by GRR-0002.
