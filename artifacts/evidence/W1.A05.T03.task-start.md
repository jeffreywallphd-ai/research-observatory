## Intended bounded design

1. Extend the native application-lock owner with one canonical versioned sign-in policy rather than creating an unrelated mutable settings owner. The canonical document uses a distinct file name so exact legacy bytes remain available for authenticated migration and recovery evidence.
2. The canonical mode is exactly `none`, `windows-password`, or `windows-hello`. It carries only the existing bounded profile name and timeout plus a monotonic revision/fingerprint needed for compare-and-swap publication. Unknown fields, modes, or versions fail locked.
3. Startup precedence is fail-closed:
   - valid canonical policy -> use it;
   - invalid/unreadable canonical policy -> locked invalid state, never fall back to legacy or `none`;
   - no canonical policy plus an exact valid legacy v1 profile -> resolve/migrate to `windows-password`, preserving profile name and zero/nonzero timeout exactly and leaving the predecessor bytes intact;
   - neither file present -> explicit in-memory `none` default;
   - invalid/unreadable legacy state with no canonical policy -> locked invalid state requiring approved same-user recovery.
4. A two-step native transition protocol separates proof from confirmation/publication. `prepare` authenticates the required current provider, then verifies the destination provider when protected, and returns a short-lived, single-use, cryptographically random opaque proof bound to the exact source revision/bytes, target policy, native generation, and operation class. It changes no policy. `commit` accepts only that proof after the UI's deliberate confirmation and atomically publishes if every binding is still current.
5. Explicit password recovery uses a separate native operation and the unchanged current-process `EqualSid` password provider. It may prepare a protected-to-`none` or corrupt/unavailable-provider reset, but still requires the later warning/confirmation and proof-bound commit. Session possession, confirmation alone, audit state, or a renderer assertion never authorizes reduction.
6. One native transition reservation exists at a time. Cancellation, denial, provider unavailability, busy, failure, panic, expiry, replay, stale generation/revision, write failure, crash before replace, or concurrent update consumes/invalidates pending authority as applicable and preserves the predecessor policy bytes.
7. Runtime lock behavior follows the committed mode: `none` cannot enter an ordinary manual/idle/restart login gate; either protected mode retains manual lock, zero-minute manual-only behavior, nonzero inactivity/restart locking, native-only provider selection, and success-only unlock authority. Invalid/corrupt protected state stays locked and exposes only deliberate recovery.
8. Publish a strict versioned native/renderer policy and transition-result contract for T04. T03 does not render the new experience.

### Adversarial-preflight decisions incorporated before product edits

- **Cross-process CAS:** canonical load/migration/publication will use a release-authoritative Windows named mutex derived from the canonical policy path, with automatic crash release. Every prepare captures exact canonical and legacy presence, byte hashes, canonical revision, native generation, and stable parent/destination file identity. Under the mutex, commit reopens and revalidates that authority immediately before replacement. A canonical file that appears during legacy migration wins; migration never replaces it. Staging names include cryptographically random material rather than only a PID. Parent/destination reparse identity is rejected at open and rechecked at publish. Pre-replace failure leaves predecessor bytes exact; a completed replace is authoritative even if the caller loses the response.
- **One verification arbiter:** ordinary unlock, configured-provider transition proof, and explicit password-recovery proof share the existing native verification reservation, generation, backoff, panic cleanup, and invalidation rules. Native code chooses the current/destination provider and obtains the main-window HWND; the renderer cannot supply a provider, outcome, HWND, or recovery class. Invalid/corrupt policy denies ordinary unlock and Core start and exposes only the distinct native password-recovery operation.
- **One-time transition capability:** the renderer receives random opaque bytes once, while native memory retains only their digest plus exact source authority, normalized target bytes/hash, operation/proof class, completed provider sequence, native generation, monotonic expiry, and pending/committed state. Commit consumes pending authority atomically. A repeat of the same handle after publish-but-response-loss returns the stored committed receipt without re-verification or re-publication; every other replay, expiry, target substitution, source change, or restart is denied. The handle is never persisted and restart invalidates it.
- **Revision rules:** canonical creation/migration starts at revision `1`; each committed mutation increments exactly once; `u64::MAX` is terminal and cannot wrap. Within a live authority boundary, the same revision with different bytes is a conflict. The exact source byte hash, not revision alone, controls compare-and-swap.

## State and authority matrix

| Source | Requested target | Required proof order | Publish authority | Failure state |
|---|---|---|---|---|
| `none` | `none` profile change | none, but exact source revision/generation required | native proof/token or bounded no-op result; no protection reduction | predecessor bytes unchanged |
| `none` | password | destination password/current-process `EqualSid` | proof-bound confirmation commit | remains `none` |
| `none` | Hello | destination OS-owned Hello for current user | proof-bound confirmation commit | remains `none` |
| password | password/profile change | current/destination password once | proof-bound confirmation commit | remains prior password policy |
| Hello | Hello/profile change | current/destination Hello once | proof-bound confirmation commit | remains prior Hello policy |
| password | Hello | current password, then destination Hello | proof-bound confirmation commit | remains password |
| Hello | password | current Hello, then destination password | proof-bound confirmation commit | remains Hello |
| protected | `none` | configured current provider, or separate explicit password recovery | proof, warning, confirmation, then commit | remains protected |
| corrupt/unknown/unavailable protected state | reset/`none` | separate explicit password recovery only | recovery proof, warning, confirmation, then commit | remains locked and byte-stable |

Authority-bearing fields are the canonical schema/document version, mode, profile name, inactivity timeout, revision/source fingerprint, native lock generation, transition operation, target-policy fingerprint, opaque proof ID, issue/expiry time, use state, and recovery-vs-configured-provider proof class. The renderer controls none of those except proposing bounded target values and returning the opaque proof for commit.
