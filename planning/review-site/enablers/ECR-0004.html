## 2. Wave and capability initiation assessment

### 2.1 Product vision and best-practice fit

Research Observatory is local-first and researcher-controlled. For a typical
single-user Windows PC, the signed-in Windows account is a proportionate local
access boundary; an unconditional second password prompt adds friction without
creating a second operating-system account boundary. Researchers with stronger
local-presence requirements should be able to opt into an OS-owned verifier
without the application handling a PIN or biometric.

The selected design therefore makes no app reauthentication the default, keeps
the current same-user Windows-password verifier as an explicit option, and adds
Windows Hello as the preferred convenience verifier when configured. It does
not weaken project encryption, filesystem permissions, Core isolation, privacy
or egress policy, audit and lineage, or later remote identity.

### 2.2 Current implementation assessment

The tested implementation already has a strong native-supervisor boundary:
`application_lock.rs` owns lock state and calls the Windows credential UI plus
`LogonUserW`; a successful token must have the same SID as the desktop process.
No profile already behaves like an unlocked first run, but this is an implicit
absence of configuration rather than a versioned policy. The renderer currently
hosts a local-profile lock dialog, and the approved static settings page is
project-scoped rather than application-scoped.

A valid persisted `application-lock-profile.v1.json` is not equivalent to no
login. Even with `inactivityTimeoutMinutes: 0`, it is a user-selected
Windows-password/manual-lock profile. A nonzero timeout additionally locks on
restart and inactivity. ADR-0018 permits corrupt-profile replacement only after
successful same-user reauthentication and explicit reconfiguration.

The implementation aligns with ADR-0018's placement and same-user guarantee.
Its weaknesses for this outcome are the verifier-specific coupling, lack of a
Windows Hello adapter, lack of an explicit mode/migration contract, and lack of
an app-wide security-settings surface. The amendment preserves the strong
native boundary and repairs only those prerequisites.

### 2.3 Refactor disposition

Only `W1.A05.T01` is technical-debt refactoring. It is a bounded provider
seam, not a redesign of project security or desktop supervision. On the exact
approved W1 baseline it is 5 of 194 estimate points (2.6%). The repository owner
explicitly directed that this authentication refactor be completed in W1
without applying the 15% planning cap. The packet records that exception only
for T01; the actual allocation is below 15% regardless. T02–T04 are new product
work. No major refactor is authorized.

  busy, cancelled, denied, and failed states.

  fabricate success.

### 5.3 W1.A05.S02 — configurable local sign-in and application settings

- Store exactly `none`, `windows-password`, or `windows-hello` in a versioned,
  application-wide configuration. New or absent legacy state migrates to
  explicit `none`; every valid persisted v1 lock profile migrates to
  `windows-password` while preserving profile name and inactivity timeout.
- Enabling a protected mode verifies its provider before atomic publication.

  app remains locked and directs the user to Windows/provider recovery.
- A valid v1 zero-minute profile remains a password/manual-lock profile with
  inactivity locking disabled. A nonzero timeout preserves restart and
  inactivity locking. Cancellation, denial, write failure, or unavailable
  destination leaves the prior config byte-stable.

## 9. Alternatives

1. **Provider seam, Hello adapter, explicit configuration, and app-level
   settings — selected.** It preserves the strong native boundary while making
   the average-user default proportionate and the stronger modes optional.
2. **Keep password-only lock.** Rejected because it retains unnecessary default
   friction and does not satisfy the requested Hello or configuration outcomes.
3. **Replace password directly with Hello.** Rejected because Hello may be
   unavailable or policy-disabled and because users requested all three modes.
4. **Put the controls in Project Settings.** Rejected because the setting
   applies to the desktop application and Windows account, not a project.
5. **Implement a custom PIN.** Rejected because the app would become a
   credential verifier and secret store without adding an OS security boundary.
6. **Silently fall back when Hello fails.** Rejected because it hides a
   protection change and makes cancellation or policy denial unsafe.
7. **Defer the work to a later Wave.** Available, but it would leave the W1
   local-runtime experience inconsistent with the requested default and require
   another future governed experience change.
