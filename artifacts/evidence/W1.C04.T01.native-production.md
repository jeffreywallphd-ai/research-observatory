## Observed behavior

with no project open and Core ready. Ctrl+K visibly focused Find a command.
Alt+Space opened the standard Windows menu while the application stayed healthy.
Escape visually hid the menu. The first following Tab did not move the visible
focus; a second Tab focused Open local projects, and Enter opened the native

No pointer action was used to recover that navigation.

Further keyboard-only standard-menu checks passed: Move followed by Right moved
the window, and Escape restored its original position; Size followed by edge
selection and Right increased width, and Escape restored the original size.
Selecting Close from the menu exited normally. Four space-triggered sent calls
returned in 0.0651–0.0782 ms; their private scalar replays entered with sender
state 0. The four replay spans contained 22, 6, 7 and 8 router returns. Across
234 observed router entries, maximum entry gap was 1017.6385 ms and maximum
router span was 1.0131 ms. These diagnostic timings are not performance budgets
or independently matched decoded-invoke receipts.

The same fixture was restarted as a fresh whole-application session: no
credentials, no project open, and Core ready. Repeating Ctrl+K → Alt+Space →
Escape left the input visibly focused. A settled observation still had no
native menu-loop exit. The first subsequent Tab coincided with loop exit but
did not move visible focus, including on a later settled screenshot.
The replay ran from 31311.0942 to 69476.0662 ms; native EXIT entered at
69475.9338 ms. Do not count this as immediate keyboard-restoration PASS.

unproved. The owner was offered a physical-keyboard comparison; no answer had
arrived when the window was closed to continue automated checks. No forced
menu cancellation, input hook, timeout or policy workaround was introduced.
