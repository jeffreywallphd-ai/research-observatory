## 2. Wave and capability initiation assessment

### 2.1 Product vision and best-practice fit

Research Observatory is local-first and researcher-controlled. For a typical
single-user Windows PC, the signed-in Windows account is a proportionate local
access boundary; an unconditional second password prompt adds friction without
creating a second operating-system account boundary. Researchers with stronger
local-presence requirements should be able to opt into an OS-owned verifier
without the application handling a PIN or biometric.

The selected design therefore makes no app reauthentication the default, keeps
the current same-user Windows-password verifier as an explicit option, and adds
Windows Hello as the preferred convenience verifier when configured. It does
not weaken project encryption, filesystem permissions, Core isolation, privacy
or egress policy, audit and lineage, or later remote identity.

### 2.2 Current implementation assessment

The tested implementation already has a strong native-supervisor boundary:
`application_lock.rs` owns lock state and calls the Windows credential UI plus
`LogonUserW`; a successful token must have the same SID as the desktop process.
No profile already behaves like an unlocked first run, but this is an implicit
absence of configuration rather than a versioned policy. The renderer currently
hosts a local-profile lock dialog, and the approved static settings page is
project-scoped rather than application-scoped.

The implementation aligns with ADR-0018's placement and same-user guarantee.
Its weaknesses for this outcome are the verifier-specific coupling, lack of a
Windows Hello adapter, lack of an explicit mode/migration contract, and lack of
an app-wide security-settings surface. The amendment preserves the strong
native boundary and repairs only those prerequisites.

### 2.3 Refactor disposition

Only `W1.A05.T01` is technical-debt refactoring. It is a bounded provider
seam, not a redesign of project security or desktop supervision. On the exact
approved W1 baseline it is 5 of 194 estimate points (2.6%). The repository owner
explicitly directed that this authentication refactor be completed in W1
without applying the 15% planning cap. The packet records that exception only
for T01; the actual allocation is below 15% regardless. T02–T04 are new product
work. No major refactor is authorized.

## 4. Governed experience decision

The proposed reference is
[`ECR-0004-experience-proposal.md`](ECR-0004-experience-proposal.md), with the
reviewable HTML mock-up in
[`ECR-0004-application-settings-reference.html`](ECR-0004-application-settings-reference.html).
It establishes:

- a distinct application-level Settings destination, not an extension of
  project settings;
- exactly three sign-in modes with `No login` labeled as the default;
- OS-owned password and Hello prompts, with no credential, PIN, or biometric
  storage by Research Observatory;
- explicit verification before enabling or changing providers;
- explicit warning and confirmation before reducing protection to `No login`;
- no silent fallback or downgrade;
- fail-locked handling for malformed enabled-mode configuration;
- explicit Hello availability, denial, cancellation, failure, and recovery
  states; and
- keyboard, focus, announcement, responsive, reduced-motion, and WCAG AA
  obligations inherited from Academic Minimal.

`No login` removes only Research Observatory startup/manual/idle
reauthentication. The page must not imply that it disables Windows account
access, encrypted storage, project privacy, Core isolation, or audit controls.

### 5.2 W1.A05.S01 — provider refactor and Windows Hello

#### W1.A05.T01 — provider-neutral native verification contract (L, refactor)

- Separate lock lifecycle/state from provider invocation while retaining the
  native supervisor as the sole unlock authority.
- Preserve current Windows-password behavior and the same-process-user SID
  guarantee.
- Define typed outcomes for success, cancellation, denial, unavailability,
  busy, and failure without translating them into silent fallback.
- Preserve startup, manual-lock, inactivity, restart, and redacted-error
  behavior unless the configured mode explicitly disables app lock.
- Add focused unit/contract tests proving parity and failure isolation.

#### W1.A05.T02 — Windows Hello native adapter (L, new product work)

- Invoke an OS-owned Windows Hello user-presence API for the current interactive
  Windows user; the app never receives a PIN or biometric template.
- Distinguish checking, available, not present, not configured, policy-disabled,
  busy, cancelled, denied, and failed states.
- Keep the application locked after cancellation, denial, unavailability, or
  failure; never silently switch providers or modes.
- Expose explicit same-user password recovery only after user selection and
  preserve auditable, bounded errors across the native/renderer contract.
- Add native contract, denial, cancellation, restart, and Windows-x64 adapter
  integration tests; unsupported environments must report unavailable, not
  fabricate success.

### 5.3 W1.A05.S02 — configurable local sign-in and application settings

#### W1.A05.T03 — versioned sign-in configuration and transitions (M, new product work)

- Store exactly `none`, `windows-password`, or `windows-hello` in a versioned,
  application-wide configuration; default and missing legacy state migrate to
  explicit `none`.
- Enabling a protected mode verifies its provider before atomic publication.
- Switching protected providers authenticates the current mode and verifies
  the destination provider before publication.
- Disabling protection requires explicit confirmed intent. Cancellation,
  denial, write failure, or unavailable destination leaves the prior config
  byte-stable.
- Malformed/unreadable enabled configuration fails locked. A deliberate reset
  to no login is locally audited and cannot occur as fallback.
- Add migration, atomicity, rollback, corruption, restart, and concurrency
  tests.

#### W1.A05.T04 — Application Settings security experience (L, new product work)

- Implement the approved application-level Settings route and Security &
  sign-in page without conflating it with Project Settings.
- Render current/default mode, prerequisites, Hello availability, lock preview,
  provider-specific recovery, and protection-reduction confirmation.
- Connect the UI only through typed application/native contracts; never expose
  credential material or project/research content on a locked surface.
- Preserve the current project and guided-workflow position when entering and
  leaving application settings.
- Prove keyboard, focus, announcement, zoom/reflow, theme, reduced-motion,
  cancellation, denial, failure, recovery, restart, and no-silent-downgrade
  behavior with conformance to `RO-UI-ACADEMIC-MINIMAL-1.4`.

## 9. Alternatives

1. **Provider seam, Hello adapter, explicit configuration, and app-level
   settings — selected.** It preserves the strong native boundary while making
   the average-user default proportionate and the stronger modes optional.
2. **Keep password-only lock.** Rejected because it retains unnecessary default
   friction and does not satisfy the requested Hello or configuration outcomes.
3. **Replace password directly with Hello.** Rejected because Hello may be
   unavailable or policy-disabled and because users requested all three modes.
4. **Put the controls in Project Settings.** Rejected because the setting
   applies to the desktop application and Windows account, not a project.
5. **Implement a custom PIN.** Rejected because the app would become a
   credential verifier and secret store without adding an OS security boundary.
6. **Silently fall back when Hello fails.** Rejected because it hides a
   protection change and makes cancellation or policy denial unsafe.
7. **Defer the work to a later Wave.** Available, but it would leave the W1
   local-runtime experience inconsistent with the requested default and require
   another future governed experience change.
