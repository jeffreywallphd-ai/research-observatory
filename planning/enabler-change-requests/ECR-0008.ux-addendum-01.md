## Directory-selection design

Use one reusable `DirectoryPickerField` composition with a visible label,
helper text, an explicitly named **Choose folder… / Change folder…** button,
and selectable, wrapping read-only location text. Do not use a free-text path
input, a hidden editable fallback, browser `webkitdirectory` enumeration, or a
custom imitation filesystem tree. The field renders state and requests a
selection; it owns no filesystem authority.

- **Create:** the user enters a human project name, chooses an existing parent
  folder in the native dialog, chooses the governed use case and writes the
  objective. The application proposes the new child folder name from the project
  name and shows the complete destination as read-only text before Create.
  Remove the separate required directory-name input. Derive a stable 1–64
  character ASCII slug accepted by the unchanged Core contract; use a stable
  `project-<short random identifier>` suggestion when the display name has no
  usable slug, and prefix Windows reserved device names. Do not change a proposed
  destination during a request or ambiguous retry. An existing destination is
  never overwritten: retain the form and offer renaming the project or changing
  the parent. Do not silently create numbered duplicates after a failed call.
- **Open:** choose the existing project folder, display its location, then use
  the explicit Open action. Core remains responsible for validating the package,
  exclusive access, compatibility and read-only/backup-first recovery.
- **All directory inputs:** inventory every implemented W1 renderer form before
  closure and route every editable directory location through the same control.
  The current inventory is the two absolute location fields plus the creation
  directory-name field. Read-only current-project and diagnostic-result paths
  are outputs, not editable selection fields. Future already-planned W1 directory
  inputs use the same component when implemented; no speculative future screen
  or directory-management feature is authorized.
- **Initial location:** use a native known-folder suggestion or the field's
  already selected, validated location. Never hard-code a username or require
  the user to know a path. Failure to resolve a suggestion opens the ordinary
  native default location; it does not invent or create a directory.
- **Cancellation/failure:** Cancel and Escape preserve the previous value and
  all entered form data, announce cancellation where useful, restore focus to
  the initiating button and perform no project action. Picker failure offers a
  plain-language retry, not raw exception output or a text-path workaround.
  Prevent overlapping dialogs and duplicate form submission.

Selecting a folder does not grant access, open or create a project, enumerate
its contents into the renderer, or start a privileged operation. Normal Core
path validation, protected-installation exclusions, reparse/redirect checks,
exclusive locks, atomic creation and no-overwrite behavior remain mandatory.

## Native and recovery boundary

Use a purpose-specific typed command through the existing Tauri native boundary,
bound to the application main window. For Windows x64, reuse the pinned Windows
crate with the minimal COM/Shell feature additions to call the system folder
picker. Do not add a general renderer filesystem capability, arbitrary command
execution, shell-open capability, or a broadly permissioned dialog plugin.
The narrow adapter is replaceable at the native platform boundary in W6; this
does not claim macOS/Linux qualification now.

The request permits only a bounded purpose (`create-parent` or `open-project`)
and optional validated previous location. The response distinguishes selected,
cancelled, unavailable and failed; only selected carries a location. Reject
unknown fields, non-filesystem results, invalid encoding/paths and unsupported
purposes. Native code must preserve current Windows user/local-directory
restrictions; a dialog selection is not evidence that a path is safe.

Obtain an application-lock protected-action generation before showing the
dialog; do not hold the Core/supervisor mutex while the user selects. Revalidate
that generation before publishing a result. Closing or locking the application
while a dialog is pending must dismiss it, discard its result, clear path/form
state from the protected view and never restore it after a new unlock session.
Returning to an unmounted/replaced form must not update a newer form. Only one
native dialog may own focus at once, and cleanup must release its guard on
cancel, error, close, lock, thread failure and normal completion.

For Local Projects, distinguish catalog loading, Core starting/not ready,
catalog failure, input validation and project-operation failure. A failed catalog
load is not a failed project mutation. Preserve a bounded actionable code and
safe help text; do not expose native exception text, paths or credentials in
logs or locked/recovery surfaces. Retry may reload the catalog or explicitly
retry Core startup, but must not automatically replay create/open/archive/delete.
Do not present a fabricated catalog as fallback or weaken catalog identity.

1. All six documented findings and original F01/F02 are replayed; no accepted
   test or negative case is deleted to get a pass.
2. Generated request -> compiled native supervisor -> actual disposable Core
   proves catalog load and project creation with a multiline objective, close,
   reopen, preserved workflow selection and the existing lineage read. A stubbed browser invoke is not
   proof of this boundary. Authenticated cold start, not-ready, service failure,
   explicit recovery and no-mutation-on-catalog-failure are covered.
3. Exact catalog and lineage shapes pass; method/path/query/body/header substitutions,
   unknown endpoints and invalid narrative controls remain denied. Repair the
   generator, not only its generated TypeScript output.
4. Real Windows folder dialog selection and cancellation work with keyboard,
   focus return, accessibility, window ownership and main-window close/lock.
   Native tests cover lock-generation changes before/after selection, duplicate
   requests, late results, non-directory/non-filesystem selection, redirects,
   inaccessible/deleted folders and denied locations. No broad permissions or
   filesystem enumeration are introduced.
5. Selecting/cancelling never creates/opens anything. Core-side no-overwrite,
   staging/recovery, locks and package validation are exercised with disposable
   fixture directories only. Preserve Unicode/spaces in selected parent paths;
   verify generated-name bounds, empty/Unicode-only names, device names, long
   names, collisions and stable request/retry identity.
6. Actual desktop/compact sidebar bottom meets the footer boundary on short and
   long pages. Narrow stacked navigation remains reachable and does not overlap
   content/footer. Both themes, 200%-effective layout, reduced motion, keyboard
   navigation and long selected-location text pass without horizontal page
